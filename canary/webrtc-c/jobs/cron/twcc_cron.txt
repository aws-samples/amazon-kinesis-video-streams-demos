# TWCC network-shaped storage canary cron entries (RPi5).
#
# Exercises the media service's TWCC (bitrate adaptation) on the ingest path: the
# master's uplink is shaped with a netns mid-path router + tc/netem so the
# TWCC-aware master's encoder must track the available bandwidth. Verified via
# CloudWatch metrics (OutgoingBitrate / EstimatedBitrate / DelayTrend), sliced by
# RUNNER_LABEL.
#
# STEADY-STATE, ONE CONDITION PER JOB (TWCC_PROFILE): each job HOLDS a single
# network condition for the whole run, so RUNNER_LABEL maps 1:1 to the condition
# and its metrics have a clear expected value you can alarm on:
#     RpiTwccGood        -> ~2 Mbps (encoder near MAX)
#     RpiTwccCongesting  -> well under 500 kbit
#     RpiTwccBad         -> near the 100 kbps floor
#     RpiTwccRecovering  -> ~1.5 Mbps range
# (A cycling variant that sweeps all profiles — for transition/ramp dynamics —
#  is at the bottom, commented out; leave TWCC_PROFILE empty to cycle.)
#
# Prerequisites (see docs/rpi5-setup-sop.md "Phase 10"):
#   - Node onboarded via rpi-onboard.sh (installs /usr/local/bin/twcc-net +
#     /etc/sudoers.d/twcc-canary + iptables + gstreamer1.0-plugins-ugly).
#   - Channel-owner account (232283333863) on the media-service twcc-shadow-mode
#     allowlist for AWS_DEFAULT_REGION (else TWCC won't negotiate).
#   - A dedicated node label (rpi5-twcc) — all 4 jobs share one gst=ON build
#     (same CANARY_MEDIA_SOURCE=testsrc -> same .build-flags -> cached), so they
#     don't thrash each other, but DO keep them off a disk-path node.
#   - A webrtc-storage-viewer node exists (or drop JS_STORAGE_VIEWER_JOIN).
#
# For the initial single-Pi test on 002, set MASTER_NODE_LABEL=rpi5-002 (or add
# the rpi5-twcc label to that node). Schedules are staggered 5 min apart so the
# 4 jobs don't collide on the node's single executor.

# RpiTwccGood
